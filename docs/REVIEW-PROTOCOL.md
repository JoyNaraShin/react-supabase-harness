# Review Protocol — 비판 리뷰는 위임한다

> 경로 표기: 이 문서의 `${CLAUDE_PLUGIN_ROOT}` 는 이 파일이 들어 있는 `docs/` 의 상위 폴더(플러그인 설치 경로)다. 문서 본문은 치환되지 않으므로 이 파일을 Read 한 경로에서 풀어 쓴다.

사용자가 작업물(코드·아키텍처·플랜·하네스 설정 자체·문서)에 대해 **비판적 리뷰·감사·품질 평가·"이거 괜찮아?"류 점검**을 요청하면, 메인 세션이 직접 평가하지 말고 아래 프로토콜을 따른다.
`hooks/review-protocol.sh`(UserPromptSubmit)가 리뷰 요청을 감지하면 이 문서를 읽으라고 주입한다 — 상주 컨텍스트가 아니라 필요할 때만 들어온다.

## 왜
메인 세션은 지금 다루는 코드를 "내가 설정대로 굴리는 내 환경"으로 인식한다. 그래서 무의식적으로 관대하게·방어적으로 읽고, 자기가 만든 코드라고 여겨 날 선 비판을 못 한다. 비판 리뷰의 핵심 가치는 **"내가 안 짰다"는 독립 컨텍스트**인데 메인 세션이 직접 하면 그게 깨진다. 이 보정을 사용자가 매번 손으로 하지 않게 만드는 것이 이 프로토콜의 목적이다.

## 규칙
1. **메인 세션에서 직접 리뷰하지 않는다.** "내 환경/내 코드" 편향이 들어간다.
2. **Agent 도구로 독립 서브에이전트에게 위임한다.** 페르소나는 명시적으로 *"이건 네가 만든 게 아니다. 이해관계 0. 무자비하게 비판하라"* 인 외부 감사관.
3. **사안이 크면 복수의 적대적 렌즈로** 병렬 위임한다(예: 아키텍처 정합성 / 실제 안정성·빌드·배포 / 출시·운영 실패 시나리오). 각 에이전트는 **자기 디스커버리부터** 독립 수행한다 — 요약해 떠먹이지 않는다.
4. **결과는 누그러뜨리지 않고 종합한다.** 칭찬 끼워넣기·"하지만 잘한 점도" 식 완충 금지. 리스크를 먼저 말한다.
5. **종합은 산문 압축이 아니라 무손실 원장 join 이다.** 리뷰는 위임해도 *종합*을 손으로 요약하면 메인 세션의 압축 편향이 바로 거기서 작동한다(실측: 9-모듈 종합이 Critical 1건을 통째 드롭 + severity 1건 강등 → 원 리뷰어 재대조로만 적발). 아래 §종합 규약을 따른다.

## 종합 규약 — 누수는 루프가 아니라 구조로 막는다
재대조 루프는 *탐지기*지 예방책이 아니다(비싸고 사후적). **커버리지 누수는 회계로, 충실도 누수는 좁힌 적대 체크로** 막는다.

1. **모든 reviewer 는 리포트 끝에 machine-readable 결함 원장**(`id | severity | 축 | 위치 | 한 줄`)을 emit 한다(각 reviewer agent 스펙이 강제). 본문 Finding 과 1:1, ID 안정.
2. **종합 = 원장 join, 요약 아님.** 모든 `(agent, Fn)` 이 `목적지 + 처리(merged/deferred/rejected + 사유)` 행을 가져야 한다. 빈칸·침묵 드롭 금지 — 떨어뜨리려면 `rejected + 사유`를 **명시**한다.
3. **severity 운반.** 항목 severity 를 그대로 옮긴다. 테마/wave/버킷 헤더가 항목 severity 를 **덮지 못한다**(강등 금지).
4. **보존 검사(루프의 싼 대체).** 모듈별 `리포트 finding 수 == 종합 표 행 수`. 불일치 = 누락 → 메꾼다. 에이전트 재스폰이 아니라 카운트 1줄.
5. **적대 재대조는 부분집합에만.** 커버리지는 4로 이미 보장. 판단이 개입한 행(`처리=merged/rejected`)만 독립 에이전트로 재확인 — 전수 재스폰 금지.
6. **산문 요약은 그 표에서 렌더.** 표가 SoT, 사람 읽는 글은 파생.
7. **집행은 스크립트가 한다 — 메인 세션 암산 금지.** 위 2·4·5의 기계 부분은 `${CLAUDE_PLUGIN_ROOT}/scripts/synthesize.py`가 수행한다: 리뷰어 리포트들을 md 파일로 저장 → **모드 A**(`synthesize.py r1.md r2.md ...`)로 원장 파싱·행 수 집계·join 표 스켈레톤(목적지·처리 빈칸) 생성 → 메인 세션은 빈칸만 채우고 → **모드 B**(`--check joined.md r1.md ...`)로 누락·severity 강등·재대조 큐를 기계 검증(불통과 시 exit 1 — 메꾸고 재실행). 압축 편향의 주체(메인 세션)가 방어의 유일한 집행자가 되지 않게 하는 배선이다.
8. 🔴 **보존 검사는 "표에 적혔나"만 본다 — "본문에 반영됐나"는 안 본다.** 모드 B가 검사하는 건 원장 행의 *존재*와 severity 문자열이지, `처리=merged`가 실제 산출물에 반영됐는지가 아니다. 실측: 종합 표에 merged 로 적어둔 2건(Critical·High)이 본문에 한 글자도 안 들어간 채 exit 0 통과했고, 독립 검증관이 grep 으로만 잡았다. → **`merged` 표기는 반영의 증거가 아니라 반영하겠다는 계획이다.** 표를 채운 뒤 반드시 §수정 검증 규약으로 넘어가고, 검증관에게 "표가 merged 라고 주장하는 항목이 본문에 실재하는지"를 명시적으로 확인시킨다.
   - 🔴 **목적지가 산출물 본문이 아닐 때 더 잘 샌다.** `처리 = "이슈에 기록"·"다음 단계로 이월"`처럼 **본문 밖을 목적지로 적은 행**은 글을 쓰다 자연히 이행되지 않아 표에만 남기 쉽다(같은 세션 2건 재발). → 검증관에게 **그 목적지 파일까지 grep 시킨다.** 기록형 처리는 표를 채우는 그 자리에서 즉시 이행한다.

## 수정 검증 규약 — 리뷰가 낸 수정은 메인 세션이 자기인증하지 않는다
리뷰 위임과 종합을 독립화해도, **그 리뷰가 찾은 결함을 메인 세션이 손으로 고치고 다시 메인 세션이 "맞다"고 선언하면** §왜의 편향이 *수정 단계로* 그대로 되돌아온다(실측: 인증 스캐폴드 RLS Critical 수정을 메인 세션이 적용 후 검증 없이 "완료·클린" 선언 → 재검증에서 첫 리뷰가 놓친 Critical 이 하나 더 나왔다).

1. **"수정 적용됨" ≠ "완료".** 리뷰발(發) 수정을 적용한 뒤엔 상태가 *수정 적용됨·검증 대기*다. 검증을 통과하기 전에 "완료/클린/해결"이라 보고하지 않는다.
2. **미묘한 수정은 독립 검증에 위임한다.** 정확성이 미묘한 것(보안·RLS·동시성·SQL 시맨틱·프로토콜 계약, 그리고 널리 복제되는 골격)은 원 리뷰어 주장·메인 세션 요약을 **믿지 말고** 새 독립 에이전트가 처음부터 재판정한다. 가능하면 실측(실행·테스트)으로, 불가하면 공식 문서 근거로 + "실측 부재" 명시.
3. **자명한 수정은 예외.** 오타·문구·참조 정정·기계 검증(typecheck/lint/build)이 곧 판정인 수정은 그 기계 게이트로 충분.
4. **결과에 따라 정정한다.** VERIFIED → 그때 비로소 "완료" 보고. STILL-BROKEN/NEW-ISSUE → 고쳐서 다시 검증. 검증 전 승리 선언 금지.

## 적용 범위
코드/아키텍처/보안/플랜 리뷰, 하네스 자체 리뷰, "안정적으로 굴러가?"류 평가, 문서 비판. — 단순 사실 질문·방금 만든 산출물의 1차 자기점검(예: 빌드 통과 확인)은 제외.
