신규 클라이언트 프로젝트의 **`/phase 0` 이전** 단계. 산출물 = `docs/plans/phase-0-domain-dossier.md` (도메인 도시에, md 1~2장 상한).

> **왜**: 도메인 지식이 없으면 초기 구조를 오너가 리뷰하지 못한 채 어물쩡 시작 → 중반에 갈아엎게 된다. 성숙 SaaS 레퍼런스를 확보하면 **백지 리뷰가 대조 리뷰가 되고**("우리 스키마엔 '수강권 정지'가 없는데 레퍼런스 3개엔 전부 있다"), 그건 도메인 비전문가도 판정할 수 있다. 이 도시에가 Phase 0 스토리맵의 재료이자 Decision Register "검토한 대안"의 공급원이자 structure-fitness 리뷰의 대조 기준이 된다.

## 0. 기존 자료 흡수 (artifact-intake — 리서치보다 먼저)
클라이언트의 **현행 자료**를 사용자에게 요청한다: 수기 장부·엑셀 사진/파일, 현행 시스템 스크린샷, 운영 규칙 메모. 디지털화 수주에선 **현행 장부의 컬럼이 곧 데이터 모델**이다.
- 받은 자료를 Read(이미지 포함)로 분석 → 엔티티·컬럼 후보, 실제 운영 규칙(환불·정지·할인 등), 클라이언트 고유 용어를 추출해 도시에의 1차 재료로.
- 자료가 없으면 도시에에 `기존 자료: 없음(순수 신규)` 명시 — 침묵 생략 금지.

## 1. 리서치 fan-out (병렬 서브에이전트 3~4개)
`general-purpose` 에이전트를 병렬 스폰(각자 WebSearch/WebFetch 자기 수행, 출처 필수):
- **R1 레퍼런스 teardown**: 이 버티컬의 성숙 SaaS **2~3개**(글로벌 1+·한국 1+ 권장)의 기능 목록·화면 구성·용어를 실측. 각각의 **엔티티 모델을 역추정**(무엇을 테이블로 갖는가).
- **R2 워크플로우·엣지 규칙**: 실제 운영자의 하루(진입점→단계→결과)와 **엣지 규칙 전수**(환불·정지·노쇼·재등록·할인·정산 등 — *중반 갈아엎기의 단골 원인*). 커뮤니티·리뷰·블로그의 실무 불만도 수집.
- **R3 한국 로컬**: 국내 관행·용어·규제(정산·현금영수증·개인정보), 국내 경쟁 서비스와 가격대.
- **R4 (선택) 권한·과금 구조**: 역할 모델(원장/강사/회원), 요금제 경계 — 권한 경계는 아키텍처가 바뀌는 결정.

## 2. 도시에 작성 (`docs/plans/phase-0-domain-dossier.md`)
```markdown
# 도메인 도시에: <버티컬>
## 0. 기존 자료 요약  (엔티티·컬럼 후보 · 클라 고유 규칙 · 없으면 "없음")
## 1. 레퍼런스 SaaS  (| 서비스 | 핵심 엔티티(역추정) | 특징적 선택 | 출처 |)
## 2. 공통 엔티티 후보  (레퍼런스 N개 중 M개가 가진 것 — 누락 시 대조 리뷰에 걸림)
## 3. 핵심 워크플로우  (운영자의 하루 — 진입점→단계→결과)
## 4. 엣지 규칙 표  (| 규칙 | 레퍼런스 처리 방식 | 우리 결정 필요? |)
## 5. 설계 갈림길  (Decision Register 대안 후보 — 예: 횟수제 vs 기간제 vs 혼합, 레퍼런스별 선택 병기)
## 6. 용어 사전  (클라 용어 ↔ 업계 용어 ↔ 코드 명명)
## 7. 출처
```
- **상한 md 1~2장.** 시장성 분석·사업 전략은 범위 밖 — 여긴 **설계 재료만**.
- §5 갈림길은 `/phase 0` 인터뷰 게이트의 질문 재료가 된다(질문마다 "레퍼런스 A는 X, B는 Y" 병기 → 오너가 답할 수 있는 질문이 됨).

## 3. 후속 배선
- 완료 보고에 §5 갈림길 개수 + "다음: `/phase 0` (인터뷰 필수)" 1줄.
- `structure-fitness-reviewer`는 도시에가 있으면 **§2 공통 엔티티·§4 엣지 규칙 대비 누락**을 적합성 축에서 대조한다(백지 정합 판정 금지).

## 금지
- 코드·스키마 작성(Phase 1+) · 시장성/사업성 판단(설계 재료만) · 출처 없는 단정 · 레퍼런스 1개만 보고 일반화 · md 2장 초과
